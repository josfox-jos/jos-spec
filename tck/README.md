# Test Compatibility Kit (TCK)

What an implementation of `application/vnd.jos+json` runs to claim conformance with this specification, offline, with no dependency beyond a JSON Schema validator.

| Level | What | How |
|---|---|---|
| Schema | every `tests/valid-*.json` validates against `schema/jos.schema.json`; every `tests/invalid-*.json` fails | `python3 -I tck/run.py` (uses `tools/validate-jos.py`; needs the `jsonschema` package) |
| Superset | every 1.0.0 vector is valid under 2.0.0 | `python3 -I tools/check-superset.py` |
| Document | the documents of `tck/documents/` (the conformance suite of the reference kernels, with fixtures): each `*.jos` has an `*.expected.json` with the exit code, the result fields, the pinned `art_` when there is one, and the promises of `PROMISES.md` it proves; a vector with `"run_document"` runs a folder and one with `"validate": null` skips validation | `python3 -I tck/run-documents.py --cli "<command of the implementation>" --expect-version <its version>`; the implementation answers `version`, `validate <file> --json` and `run <file> --json --runs <dir>` |
| Parity | two implementations run the same documents and their complete results are compared with each other (exit codes, every member of the JSON printed by `validate` and `run`, receipts, errors with their text); only what the specification allows to differ is normalized: minted identifiers (`run_`, `cap_`, … by order of appearance), `ts` and the Capability's `issued`/`expires`, `duration_ms`, receipt hashes (each recomputed and verified first) and the implementation name in `version` (the list, with the section that allows each one, is in the tool's header). The two reference kernels differ only in `jcs-numbers`, an integer outside the interoperable range of RFC 8259 Section 6 (CONFORMANCE.md Section 9) | `python3 -I tck/compare-implementations.py --a "<command of A>" --b "<command of B>" [--json]` |
| Reference implementations | the implementations attached to a release, checked against the sha256 of `reference-implementations.lock.json`, installed offline, then the document level on each | `python3 -I tools/verify-reference-implementations.py --assets <folder with the release assets>` |
| Traceability | every requirement of `SPECIFICATION.md`, the schema members it names, the vectors that cite its section and their result | `python3 -I tools/traceability.py --results <report of run-documents.py --json>` |

A vector may list `"alternatives"`, other outcomes that the specification also allows: the `tier-sandbox-*` vectors expect the refusal of a runtime that cannot confine a step (code 5), and also list the run of one that does (code 0, `isolation: "sandbox"` in the receipt). That alternative carries `"claim": "sandbox"`: this TCK cannot observe confinement from outside, and a receipt is not evidence of it (SPEC Section 6.5), so a run that matches it is reported as UNVERIFIED, never as a pass (exit code 2 when nothing fails). Proving a sandbox claim needs a suite that probes confinement from outside the process, planned for 2.1.

The document level judges what an implementation prints and its exit code. It does not observe side effects: an implementation that ran a step and then printed the expected refusal would pass it. That a refused step has no effect is checked by the conformance runner of the reference kernels, not by this TCK.

Error messages are not part of the format. An expected error `"<JSON Pointer>: <message>"` is judged by its JSON Pointer, so an implementation does not have to reproduce the wording of the reference kernels; `--strict-messages` compares the whole text and is how the reference kernels are judged.

[PROOF.md](PROOF.md) is the result for the two reference kernels, promise by promise, generated by the tool that writes the table of the README.

A claim of conformance names the version of this specification, the TCK commit, the level reached and the command output. The two reference kernels (JavaScript, Python) publish theirs in `CONFORMANCE.md` Section 9.
